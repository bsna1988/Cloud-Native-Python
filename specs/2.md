# ADR 0002: Offline-First Android Book Management

- **Status:** Accepted
- **Date:** 2026-10-21

## Context

The Android client currently reads and writes books directly through the Flask
API using Retrofit. The repository returns request failures to the UI, and the
client has no durable local book database. Adding, editing, and deleting books
therefore require the server to be reachable. Selected image files are staged
in the app cache, which Android may clear and which is unsuitable for deferred
uploads.

The Android app must allow the user to view the library and add, edit, and
delete books while disconnected, then synchronize those changes after network
connectivity returns. The existing Flask API stores books and image URLs in
SQLite and exposes list, create, update, and delete endpoints. Book IDs are
server-assigned integers. The API does not currently provide mutation
idempotency keys, server revisions, or conflict detection.

## Decision

Make the Android app offline-first, with a local Room database as the source of
truth for the UI. The Flask API remains the shared, durable server-side store;
Room is the source of truth for the Android device's immediate reads and
pending writes.

### Local persistence and UI

- Store book records, their server image URLs, sync state, and pending
  operations in Room.
- Observe Room data from the repository and render it immediately. Refreshing
  from the server updates Room rather than bypassing it to populate the UI.
- Store newly selected or captured image files in app-private persistent
  storage, not the cache directory. Keep them until the server confirms upload.
- Apply create, edit, and delete operations to Room immediately, and record
  their pending synchronization work in the same database transaction.
- Keep locally deleted server books as tombstones until their delete reaches
  the server. Deleting a book that has never synced cancels its pending create
  and removes its local files.
- Editing a locally created book updates the pending create payload instead of
  creating an unnecessary sequence of remote edits.
- Show whether the library has pending changes or a synchronization failure;
  local writes must not appear to fail just because the server is unavailable.

### Synchronization

- Use WorkManager with a connected-network constraint to schedule durable
  synchronization, including after app restarts. Also enqueue a unique sync
  request when connectivity returns or a local mutation is made.
- Replay pending operations sequentially, preserving per-book ordering. Retry
  transient network and server errors with backoff; retain pending work until
  the server confirms it.
- After pending writes are acknowledged, fetch the server library and reconcile
  it into Room. Do not overwrite rows with unsynced local changes during this
  refresh.
- Give each local book a stable client-generated UUID independent of the
  server's integer ID. Map the UUID to the assigned server ID after a successful
  create.
- Add an idempotency key to create operations and persist processed keys on the
  server. A retry after a lost response must return the original created book,
  not create a duplicate.
- Persist attachment paths and the intended image additions/removals with
  pending work so multipart uploads can safely be retried.

### Conflict policy

When the Android device has an offline change and the corresponding server
record has changed since the device's last successful sync, **the Android
device's pending change wins**. On reconnect, send the Android's current full
book state to the server; a pending delete deletes the server record. A local
update to a record deleted remotely should recreate it and update its mapped
server ID. A server-only edit to a clean local record is accepted during
reconciliation.

This is a last-writer-wins policy at the book-record level, not a field-by-field
merge. It is appropriate for the current personal-library use case and can
overwrite changes made from the web app while the Android client was offline.
The UI should make pending synchronization visible so the user can understand
that local changes have not yet reached the server.

### Offline limitations

- Browsing, manual book entry, editing, and deletion work without a network.
- Book images remain available locally while pending upload. Images already
  stored only on the server are not guaranteed to display offline unless they
  have been downloaded into a managed local cache.
- Barcode decoding can happen on-device, metadata lookup is as well hapenning on device. Image-based recognition require network access to their current services. They remain
  unavailable offline; the user can enter metadata manually.
- The web frontend is not made offline-capable by this decision.

## Implementation implications

- Add Room entities, DAOs, migrations, and repository flows for cached books,
  sync state, tombstones, and pending mutations.
- Add WorkManager and a worker that performs the ordered upload/reconciliation
  process.
- Extend the backend create API and database to support durable idempotency
  keys. Ensure image uploads and book creation are safely handled on retries.
- Adapt create, update, and delete API calls to sync from local records and
  retain pending operations on failure.
- Replace cache-directory staging for book photos with managed persistent files.
- Add tests for offline CRUD, app/process restart with pending work, retry after
  connectivity loss, duplicate-free create retries, image upload retries, and
  the selected conflict policy.

## Consequences

### Positive

- Core library operations remain usable when the Raspberry Pi or network is
  unavailable.
- The UI can display local books without waiting for a request.
- Durable local state and retryable operations reduce the risk of losing edits
  or uploaded images when the app is closed or the network drops.
- Stable client IDs and idempotent creates make synchronization safe to retry.

### Negative

- The Android app now has a local schema and migration responsibilities in
  addition to the backend schema.
- Synchronization, tombstones, attachment retention, and retry behavior add
  implementation and test complexity.
- The chosen last-writer-wins policy may replace web-side edits with an older
  Android snapshot. This is an intentional trade-off; conflict prompts or
  field-level merges can be considered if multi-client editing becomes common.
- Local copies of book images consume device storage and require cleanup after
  confirmed uploads or cancelled local books.

## Alternatives considered

### Cache server responses without an outbox

This improves offline reading but cannot reliably queue create, update, and
delete operations or persist their images. Rejected because offline writes are
required.

### Keep server as the UI source of truth and queue requests in memory

In-memory queues are lost when Android kills the process or the device
restarts. Rejected because offline changes must be durable.

### Ask the user to resolve every conflicting edit

This avoids silently replacing remote changes but adds interaction and
implementation complexity for a personal library. Rejected for the initial
version; Android's offline state wins as described above.

### Merge fields individually

The existing API does not expose record revisions or a change history, so
reliable field-level merge is not currently possible. Revisit if multiple
clients frequently edit the same books.
