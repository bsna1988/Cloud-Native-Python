# ADR 0003: Continuous Barcode Scanning for Bulk Book Entry

- **Status:** Accepted
- **Date:** 2026-10-21

## Context

The Android app can currently launch a one-shot barcode scanner from the
Add Book screen. After each scan, it looks up book metadata and fills the
form, but the user must save the book and start the scanner again. This makes
adding many books unnecessarily slow.

The existing Android app already includes ZXing Android Embedded and calls the
backend barcode lookup endpoint. The backend can create a book from book
metadata, and rejects a create when a book with the same title already exists.
The app is also adopting offline-first storage as described in ADR 0002.

The desired flow is a dedicated bulk-entry mode: start the camera once, point
it at books one by one, and have matching books added without further taps.

## Decision

Add a continuous barcode scanning mode to the Android app. Reuse ZXing Android
Embedded, which is already a dependency, and use its continuous decoding API
inside an in-app scanning screen rather than launching the current one-shot
scanner activity.

Both this continuous scanning mode and the existing one-shot scanner launched
from the Add Book screen must use portrait orientation. The scanner must not
rotate into landscape when the device is rotated.

For each newly detected barcode, the app will:

1. Normalize and validate the scanned ISBN on-device.
2. Suppress repeat frame detections for that ISBN during the current scan
   session, so a book held in view does not trigger multiple lookup or create
   requests.
3. Check the local library for an existing copy. If found, skip it and show a
   brief “already in library” indication.
4. Look up book metadata using the existing backend barcode endpoint.
5. If metadata is found and no duplicate exists, automatically add the book to
   the library without opening the edit form or requiring confirmation.
6. If no metadata match is found, skip the book and briefly show a “not found”
   indication. Do not create a barcode-only entry in this mode.
7. Continue scanning after each result, including lookup or create failures.
   Show a brief status for each result and keep recoverable failures visible
   long enough for the user to retry or manually add the book later.

Process distinct scans sequentially to preserve create order and avoid
concurrent duplicate checks. Continue accepting distinct ISBN detections while
one request is in flight by queueing them in scan order. Bound the queue and
provide a visible indication if the app cannot keep up, rather than silently
dropping scans.

The user explicitly stops the session with a visible control or navigates away.
The camera must be released when the screen is stopped, paused, or disposed.
The scanning UI displays clear progress and result feedback without requiring
the user to tap between books.

For an offline-first implementation, successful metadata lookups are inserted
into the local Room library and queued for server synchronization as specified
by ADR 0002. The metadata lookup itself requires a network connection. If it
is unavailable, show a temporary failure for that ISBN and continue scanning;
do not add an incomplete book.

## Duplicate handling

Treat the same ISBN as the same physical book for the purposes of this bulk
workflow and skip it when already present locally. The server currently
enforces duplicate titles rather than unique ISBNs, so the backend create path
must also handle a duplicate response safely: report it as already present,
do not create another entry, and allow the scanner session to continue.

## Consequences

### Positive

- Many books can be added in one uninterrupted camera session.
- Existing ZXing dependency and backend ISBN lookup can be reused.
- Per-session barcode suppression and duplicate checks prevent repeated
  detections from creating duplicate requests or entries.
- Unknown books and duplicate books do not silently pollute the collection.
- The feature can enqueue successful additions through the offline-first
  repository once ADR 0002 is implemented.

### Negative

- Continuous camera preview requires an in-app scanning UI and explicit camera
  lifecycle handling.
- Metadata lookup and creation are asynchronous. A bounded queue and per-scan
  status feedback are needed to cope with rapid scans and network latency.
- Metadata lookup is unavailable offline, even though local book browsing and
  editing are supported by ADR 0002.
- Duplicate detection by title can produce false positives for different books
  with identical titles; the backend's duplicate policy may need refinement.

## Alternatives considered

### Relaunch the existing one-shot scanner after each book

This preserves the current flow but interrupts scanning after every book and
does not meet the hands-free requirement. Rejected.

### Add another barcode-scanning library

The project already depends on ZXing Android Embedded. Rejected unless its
continuous decode API proves insufficient for supported devices.

### Add every scanned ISBN, even without metadata

This would allow offline capture but creates incomplete records and was
rejected for this workflow. Offline barcode capture can be considered
separately if users need it.

## Implementation implications

- Add a dedicated continuous scanning screen or mode using ZXing's continuous
  decode callback and Android lifecycle-aware camera control.
- Configure the existing ZXing capture activity and the continuous scanner UI
  to stay in portrait orientation.
- Add ISBN normalization/validation and per-session duplicate suppression.
- Add local-library duplicate lookup and connect successful lookup results to
  the repository's automatic create operation.
- Ensure lookup/create outcomes do not close the camera session.
- Add tests for repeated frame detections, duplicate local books, metadata
  misses, request failures, queued scans, and automatic book insertion.
