# ADR 0004: Use OpenRouter Free Vision Models for Image Recognition

- **Status:** Accepted
- **Date:** 2026-10-21

## Context

The backend currently sends book-cover images to a locally hosted vision model
through LM Studio's OpenAI-compatible chat-completions API. The model runs on
the developer's Mac, so image recognition depends on that Mac being powered on,
reachable, and serving the selected model. Local inference can also be slow.

The backend already handles image uploads and calls the local model from a
pluggable recognition strategy. It extracts title and author from the model's
JSON response, then queries OpenLibrary to obtain catalog candidates.

The goal is to stop depending on the developer's Mac and use OpenRouter's free
hosted inference tier instead. OpenRouter supports image input through its
chat-completions API and offers models with a `:free` catalog variant. Free
variants may have different rate limits and availability from paid versions;
automatic fallback to a paid model can incur charges.

Sending images to OpenRouter means book-cover images leave the Raspberry Pi and
are processed by an external hosted provider. This data-flow change is
intentional.

## Decision

Replace the LM Studio-specific transport with an OpenRouter vision recognition
strategy. The backend sends book images and a constrained extraction prompt to
OpenRouter's OpenAI-compatible chat-completions endpoint:

`https://openrouter.ai/api/v1/chat/completions`

The strategy continues to return title and author candidates to the existing
OpenLibrary lookup flow. Barcode recognition remains first in the recognition
pipeline; vision recognition is used as the secondary strategy.

### Model selection and cost control

- Configure the model ID outside source code using a server-side environment
  variable. The configured ID must identify a current OpenRouter model with
  image input and a `:free` variant.
- Check the model catalog for both vision capability and a free variant before
  changing the configured model. Model availability and IDs can change.
- Never silently fall back to a paid model. If configured free models are
  rate-limited, unavailable, or cannot accept images, report recognition as
  unavailable and leave the rest of the app usable.
- If a fallback list is used, every entry must be explicitly a `:free` model
  with image input. Do not use a paid model as a fallback.
- Treat free-tier limits and availability as best-effort, not an availability
  guarantee. Surface provider rate limits and temporary outages clearly, and
  use bounded retries with backoff rather than repeatedly resubmitting images.

### Credentials and image handling

- Keep the OpenRouter API key only on the backend, supplied through a protected
  environment variable or deployment secret. Never put it in Android or
  frontend code, commit it, or return it in API responses.
- Forward only the uploaded image(s) required for recognition and the
  extraction prompt. Do not include unrelated book data or user identifiers.
- Preserve the existing upload cleanup behavior. Do not log image contents,
  base64 payloads, API keys, or full provider request bodies.
- Document that image recognition sends book-cover images to OpenRouter and
  review the provider's data-handling terms before production use.
- Keep image payloads within the existing upload limits; avoid sending
  unnecessary images and resize/compress oversized inputs when required.

### Recognition output

- Request a small JSON object containing `title` and `author`, with empty
  strings for unreadable fields and an instruction not to guess.
- Validate the response shape and field types before using it.
- Treat malformed output or an empty result as a failed recognition attempt;
  do not convert invalid responses into success-shaped book records.
- Query OpenLibrary only when the model returns a usable title. If the lookup
  fails, preserve a result from the recognition strategy only when it contains
  a usable title or author, following current application behavior.

## Consequences

### Positive

- Recognition no longer depends on the developer's Mac or a locally running
  LM Studio server.
- The Raspberry Pi does not need to host or load a large vision model.
- OpenRouter provides a common API and allows changing compatible vision
  models through configuration rather than rewriting recognition flow.

### Negative

- Book-cover images are sent to an external provider, introducing a privacy
  and data-handling dependency.
- Free models can be rate-limited, unavailable, changed, or removed; response
  speed and reliability are not guaranteed.
- Recognition requires the Raspberry Pi to have internet connectivity even
  when the local app and library are available on the LAN.
- The deployment must securely configure an OpenRouter API key.
- Vision-model accuracy and output formatting may vary between model choices,
  requiring regression tests when changing the configured model.

## Alternatives considered

### Continue using LM Studio on the developer's Mac

This keeps inference local but leaves the Pi dependent on the Mac remaining
powered on and reachable. Rejected because eliminating that dependency is the
primary goal.

### Run a vision model on the Raspberry Pi

This avoids an external inference provider but adds model deployment,
performance, and memory constraints on the Pi. Rejected for this iteration.

### Use a paid hosted model

A paid model may improve availability or quality but introduces ongoing
inference costs. Rejected for the initial implementation in favor of a
free-tier-only configuration.

## Implementation implications

- Replace `LmStudioVisionRecognitionStrategy` with an OpenRouter-backed
  strategy and update application configuration to read the model ID and API
  key from environment variables.
- Send OpenRouter authentication in the HTTP `Authorization: Bearer` header.
- Keep use of the existing `requests` dependency; no inference runtime or model
  weights need to be installed on the Pi.
- Handle HTTP 429 and provider availability errors explicitly, with bounded
  retry/backoff and useful server-side logs that exclude credentials and
  image payloads.
- Add tests for request URL/auth/model configuration, image encoding, valid
  response parsing, malformed responses, rate limiting, and provider errors.
- Configure the Pi's systemd service with the API key using a protected
  environment file or equivalent secret mechanism, not a checked-in unit-file
  value.
- Update deployment documentation to explain key provisioning and the external
  image-processing data flow.
