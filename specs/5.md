# ADR 0005: Add Books from Bookshelf Photos

- **Status:** Accepted
- **Date:** 2026-10-25

## Context

The application can recognize a single book from a cover image and can add
books through barcode scanning, but neither flow can populate the library from
a photograph of several books on a shelf. Adding a large existing collection
one book at a time is slow.

The backend already uses OpenRouter for hosted vision recognition. A bookshelf
photo presents a different recognition task from a cover photo: the model must
identify several narrow spines in one image and return multiple book
candidates. The recognition may be incomplete or incorrect, and a whole shelf
image may have small, obscured, or angled text. Automatically adding every
model result could pollute the library with duplicates or invented metadata.

The feature should let the user photograph a shelf, identify the books that
can be read, and add the results efficiently while keeping the user in control
of what enters the library.

## Decision

Add a bookshelf-photo import flow that uses a dedicated multi-book vision
recognition strategy backed by the configured OpenRouter vision model. Keep
this separate from the existing single-book cover recognition strategy, whose
output and metadata lookup behavior are designed for one book at a time.

For the initial version, process one photo per recognition operation. Users
with multiple shelves can repeat the flow for each photo. Recommend framing
one shelf or a readable section at a time rather than taking a distant photo
of an entire room or collection.

The flow is:

1. The user captures or selects a bookshelf photo and submits it for
   recognition.
2. The backend sends the image to OpenRouter and requests a structured list
   containing the readable title and author for each detected book. The model
   must not guess unreadable fields or invent books.
3. The backend validates the response and looks up metadata for each usable
   candidate through the existing metadata lookup service when possible.
   Failure to enrich one candidate must not discard other candidates.
4. The app displays the recognized candidates in a review list before adding
   anything. The user can deselect candidates and correct their title or
   author.
5. The app checks candidates against the existing library and marks likely
   duplicates. Candidates already in the library are not selected for import
   by default.
6. The user confirms the selected candidates. Only then are they added through
   the existing book-creation flow. A failure for one book must not prevent
   other selected books from being added; report per-book outcomes.

Do not create a book for a candidate with no usable title. Treat model output
as untrusted input: validate the response schema and string fields, impose
reasonable limits on candidate count and field lengths, and do not interpret
model output as executable instructions or trusted metadata.

Recognition requires network access to OpenRouter and remains unavailable
offline. Preserve the original photo only according to the existing upload
cleanup and image-retention behavior; do not retain it solely for recognition.
Clearly disclose that the bookshelf image is sent to OpenRouter for processing.
Keep the API key on the backend and do not log image contents, encoded image
data, or credentials. The feature must use only a configured free vision
model; do not fall back to a paid model.

## Consequences

### Positive

- A single photo can produce candidates for several books, reducing manual
  entry effort.
- Reviewing and correcting candidates before import limits the impact of
  recognition mistakes and accidental duplicates.
- Per-book handling allows partial success when lookup or creation fails for
  some candidates.
- A dedicated multi-book strategy avoids changing the output contract of
  existing single-book recognition.

### Negative

- Spine text is often small, curved, obscured, or photographed at an angle, so
  recognition will be less reliable than scanning a barcode or photographing
  a single cover.
- Review, editing, duplicate detection, and per-book results add UI and API
  complexity.
- A bookshelf image can contain many books and consume more provider
  processing and free-tier quota than a single-cover image.
- OpenRouter availability, free-model limits, and model behavior can change;
  the feature depends on internet access and a compatible configured model.
- A batch can be only partially recognized or imported, so the UI must make
  incomplete results and individual failures clear.

## Alternatives considered

### Automatically add every recognized book

This minimizes user interaction but risks adding hallucinated, incomplete, or
duplicate entries without the user noticing. Rejected in favor of a review
step.

### Reuse the single-book cover recognition strategy

The existing strategy returns one book candidate and is optimized for a
single cover. Extending it to return a list would mix incompatible output
contracts and complicate existing callers. Rejected in favor of a dedicated
multi-book strategy.

### Require one photo per book

This would likely improve recognition accuracy but would not address the
request to populate a library from a bookshelf efficiently. Rejected.

### Run recognition locally on the device

The current application already uses the backend and OpenRouter for image
recognition. On-device multi-book vision would add model/runtime requirements
to the client and is not part of this change.

## Implementation implications

- Add a dedicated bookshelf-photo recognition strategy that uses the existing
  OpenRouter client/configuration and returns a validated list of book
  candidates.
- Add an API flow for submitting a bookshelf image and returning independent
  candidate results without automatically creating books.
- Add a review UI that supports editing, deselecting, duplicate indications,
  confirmation, and per-book import status.
- Reuse existing metadata lookup and book creation paths where possible rather
  than duplicating their behavior.
- Apply existing image upload size limits and clean up temporary uploads on
  both success and failure.
- Keep processing bounded: limit candidate count and field sizes, and avoid
  unbounded retries or per-candidate provider calls when one model response
  can return the shelf candidates.
- Add tests for multiple candidates, malformed or partial model output,
  unreadable titles, metadata lookup failures, duplicate marking, selective
  import, partial create failures, provider errors, and cleanup.
