# ADR 0006: Hybrid On-Device Book Image Recognition

- **Status:** Accepted
- **Date:** 2026-10-26

## Context

The Android app currently uploads book-cover and bookshelf images to the
backend, which uses OpenRouter for vision recognition. This makes recognition
depend on network access and a third-party provider, whose free models can be
rate-limited, unavailable, or changed. Using a paid hosted model would add
unpredictable operating costs.

Book spines in a shelf photograph are narrow, crowded, and often angled or
partially obscured. Sending the full shelf to a small vision-language model can
make individual titles difficult to read. Running a large vision model directly
on every phone would increase app size, memory use, latency, battery use, and
device compatibility requirements.

The Android app already supports on-device barcode scanning and has a
bookshelf review flow. The review step is important because image recognition
can miss books or produce incorrect metadata; model output must not be treated
as guaranteed accurate or hallucination-free.

## Decision

Move Android book-image recognition to an on-device, two-stage pipeline:

```text
Camera or selected image
        |
        v
Small on-device book/spine detector
        |
        v
Crop and prepare each detected book region
        |
        v
Small on-device vision-language model (VLM)
        |
        v
Validate, merge, and deduplicate candidates
        |
        v
Existing review and edit flow
```

The detector identifies individual book regions in a shelf photo and provides
crops to the VLM. The VLM reads each crop and returns structured title and
author candidates. A single-cover image may use the same VLM without shelf
detection when a crop is not needed.

Candidate implementations include a compact MobileNet- or YOLO-family detector
and a small model such as SmolVLM-256M, subject to Android runtime compatibility,
model licensing, model availability, and measured performance. These are
candidates for evaluation, not fixed implementation requirements. No model
size or speed estimate is an accuracy or device-performance guarantee.

### Recognition behavior

- Run detection and VLM inference locally on the Android device. The default
  recognition flow must not upload the source image or crops to OpenRouter or
  another hosted vision provider.
- Use the existing barcode scan path when a barcode is available; do not run
  image recognition unnecessarily for a successfully identified barcode.
- Treat detector and VLM output as untrusted candidates. Validate field types,
  lengths, and candidate counts; discard invalid entries and report when no
  usable candidate is found.
- Merge overlapping detections and suppress duplicate candidates conservatively.
  Do not invent unreadable title or author text. Preserve an empty author when
  it cannot be read.
- Show candidates in the existing review flow before importing. The user can
  edit or deselect results, and likely duplicates remain visibly marked. Never
  automatically create books solely from model output.
- When on-device inference is unavailable or fails, explain that recognition
  could not be completed and allow manual entry. Do not silently switch to a
  hosted vision model. A future opt-in hosted fallback would require a separate
  decision and explicit disclosure/consent.
- Metadata catalog lookup may continue through existing backend APIs after
  on-device extraction. Such a lookup must not include the source image or
  image crops.

The prompt for a small VLM should be short and specific. For shelf crops, use
instructions such as:

> Read the book title and author printed on this book. Return only JSON with
> string fields `title` and `author`. Transcribe readable text; use an empty
> string when a field cannot be read. Do not guess or include other text.

The VLM processes individual detected crops rather than being asked to locate
all books in the original crowded shelf image. The detector is responsible for
localizing candidate book regions.

### Model runtime and evaluation

- The first Android implementation uses bundled Google ML Kit Text Recognition
  v2 for local OCR of recognized text blocks. It does not yet implement a
  book-spine detector or VLM; OCR blocks are provisional candidates shown for
  user review, with author fields left blank unless separately obtained.
- Select an Android-compatible inference runtime and model formats through a
  measured prototype before committing to a particular model/runtime pair.
- Keep model assets versioned and integrity-checked. Prefer downloading model
  assets from a trusted first-party location on demand over unnecessarily
  increasing the base application download size. Recognition must report
  clearly if model assets are missing or cannot be loaded.
- Evaluate detector recall, crop quality, title and author accuracy, duplicate
  handling, and end-to-end latency on representative devices and shelf images.
  Include low-end supported hardware, small/angled spines, glare, and partially
  occluded books.
- Bound the number of detected crops and inference work per image. Handle
  memory pressure, cancellation, and lifecycle changes without blocking the UI
  thread or retaining images longer than needed.
- Use confidence thresholds only when measured against a representative
  validation set. Low confidence should be reviewable or omitted, not presented
  as certain metadata.

This decision changes Android's image-recognition data flow. It supersedes the
hosted-provider choice in ADR 0004 and the Android recognition path in ADR 0005.
The backend recognition endpoints may remain available for non-Android clients
or compatibility, but the Android app must not depend on them for its default
image-recognition flow.

## Consequences

### Positive

- Android image recognition can work without an internet connection or
  OpenRouter availability.
- The default image-recognition path does not send personal shelf photos to a
  hosted vision provider and avoids per-image inference charges and provider
  rate limits.
- Cropping individual books gives the VLM a smaller, more focused image than a
  crowded shelf photograph.
- Existing user review remains in place to catch missed, incorrect, or
  uncertain recognition results.

### Negative

- On-device inference adds model/runtime integration, model asset delivery,
  compatibility, and regression-testing work to the Android app.
- Model downloads or bundled assets increase storage use; inference consumes
  device memory, battery, and compute resources and may be slow on low-end
  hardware.
- Book-spine detection and text recognition can still fail on small, rotated,
  reflective, or obscured spines. The two-stage pipeline does not guarantee
  clean extraction or eliminate hallucinations.
- Model updates are coupled to app or model-asset releases and must be tested
  across supported Android versions and devices.
- Catalog enrichment may still require network access even though image
  recognition is local.

## Alternatives considered

### Continue sending images to OpenRouter

This avoids shipping and running models on mobile, but keeps image recognition
dependent on network connectivity, provider availability, free-tier limits,
and external image processing. Rejected as the default Android path because
the desired outcome is local recognition without recurring inference costs.

### Run one larger VLM on the full shelf image

This avoids a separate detector but gives the model a crowded image with small
spine text and may require a larger, more expensive model. Rejected in favor of
detecting and cropping individual books before text extraction.

### Run only OCR on each crop

OCR can extract visible text but does not reliably distinguish title, author,
and other cover text without additional book-aware parsing. It remains an
alternative to evaluate if it provides sufficient quality with lower resource
use.

### Run all inference on the backend

This keeps mobile requirements small but requires network access and continues
to incur hosted-provider limits, costs, or server resource requirements.
Rejected for the default Android recognition flow.

## Implementation implications

- Add an Android recognition component that owns image preparation,
  book-region detection, crop generation, VLM inference, response validation,
  and candidate merging.
- Integrate it with single-cover recognition and the existing bookshelf
  review/import flow. Do not change the review-before-import behavior.
- Keep barcode recognition ahead of image recognition when a barcode result is
  complete.
- Choose detector, VLM, runtime, and model distribution after a device and
  accuracy evaluation; do not assume MobileNet/YOLO-Nano or SmolVLM-256M is the
  final combination before testing.
- Add instrumentation and tests for model loading, invalid model output,
  unreadable crops, overlapping detections, duplicates, cancellation, image
  cleanup, and offline operation.
- Add an evaluation set with varied shelf layouts and manually verified
  ground-truth titles/authors. Track recognition quality and latency by device
  tier before setting confidence thresholds or declaring the feature ready.
- Update Android and deployment documentation to explain local processing,
  model downloads/storage, offline behavior, and the possibility of
  recognition errors.
- Keep server-side OpenRouter credentials out of the Android app. Retain or
  remove backend recognition endpoints only through a separate compatibility
  and client-usage review.
