# ADR 0008: User-Approved Book Metadata Candidates

- **Status:** Accepted
- **Date:** 2026-10-30

## Context

Books can enter the library through barcode or image recognition, automatic
scanning, and manual entry. These paths can create records with some metadata
missing, such as an author, publication year, description, or ISBN. Users
currently have to find and enter that information themselves.

The backend already has Google Books and Open Library metadata providers and
shared lookup, caching, rate-limiting, and retry behavior. Android displays an
individual book page and uses an offline-first Room repository, so a metadata
suggestion must not block that page or bypass the existing persistence and
synchronization flow. Catalog matches can be ambiguous or incorrect and must
not silently overwrite a user's data.

## Decision

Offer catalog metadata candidates on the Android individual book page whenever
the book has one or more missing metadata fields. Android must call Google Books or Open Library directly.


### Display and acceptance

- Start lookup asynchronously when the individual book page is shown and the
  book is incomplete. Keep the existing book content usable while it runs.
- Show available candidates in a section at the bottom of the page. Display
  enough candidate metadata, including title and author where available, for
  the user to distinguish likely matches.
- Show candidates for books regardless of how they were created, including
  scanned, automatically added, and manually entered books.
- Do not request or display candidates when all supported metadata fields are
  present. Re-evaluate this condition when the displayed book changes.
- Require an explicit user selection. Selecting a candidate replaces the
  book's metadata fields with the selected candidate's values, including
  replacing existing metadata values where the candidate supplies a value.
  Preserve the book's library identity, local/server IDs, images, and sync
  bookkeeping; candidate data must not replace those.
- Persist an accepted candidate through the normal Android book repository and
  existing update/synchronization path. Do not write to Room or the backend
  merely because candidates were fetched.
- Keep manual editing available. A lookup failure or empty result must not
  prevent viewing or editing the book; report lookup failures through the
  app's normal error state rather than treating them as successful empty
  results.


## Consequences

### Positive

- Users can fill gaps in scanned and manually entered records without leaving
  the book page.
- Explicit acceptance keeps the user in control and prevents uncertain catalog
  matches from silently replacing data.
- Android queries the public catalog APIs directly, avoiding the backend's
  shared provider quota for routine detail-page lookups.
- Using the normal repository update path preserves offline-first behavior and
  synchronization semantics.

### Negative

- Catalog results may be incomplete, stale, or mismatched; users must inspect
  candidates before accepting them.

## Alternatives considered

### Automatically fill missing fields

Rejected because a plausible catalog match may refer to a different edition
or book. User approval is required before changing a record.

### Search candidates from backend

Rejected because routing routine detail-page searches through the backend
would consume the shared provider quota. Android queries the public catalog
APIs directly.

### Always show candidates

Rejected because complete records do not need enrichment, and unnecessary
lookups add latency and provider load. Lookup and candidate UI are limited to
books with missing metadata.
