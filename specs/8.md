# ADR 0008: User-Approved Book Metadata Candidates

- **Status:** Accepted
- **Date:** 2026-10-30

## Context

Books can enter the library through barcode or image recognition, automatic
scanning, and manual entry. These paths can create records with some metadata
missing, such as an author, publication year, description, or ISBN. Users
currently have to find and enter that information themselves.

The backend already has Google Books and Open Library metadata providers and
shared lookup, caching, rate-limiting, and retry behavior. Android displays an
individual book page and uses an offline-first Room repository, so a metadata
suggestion must not block that page or bypass the existing persistence and
synchronization flow. Catalog matches can be ambiguous or incorrect and must
not silently overwrite a user's data.

## Decision

Offer catalog metadata candidates from the Android book edit page. Search only
when the user explicitly taps the search button; opening or viewing a book must
not make catalog requests. Android calls Google Books and Open Library
directly. The Google Books API key is supplied at build time through local,
untracked configuration rather than hard-coded in source.


### Display and acceptance

- Start lookup asynchronously only after the user requests it from the edit
  page. Use the current title, author, and barcode form values as the query
  input. Display enough candidate metadata, including title and author where
  available, for the user to distinguish likely matches.
- Allow lookup for any book with a title, author, or barcode, regardless of how
  it was created or whether its current metadata is complete.
- Require an explicit user selection. Selecting a candidate fills the edit
  form with fields supplied by that candidate; the user can review or adjust
  these values before saving.
- Persist an accepted candidate through the normal Android book repository and
  existing update/synchronization path only when the user saves the form. Do
  not write to Room or the backend merely because candidates were fetched or
  selected.
- A lookup failure or empty result must not prevent editing; report lookup
  failures through the edit screen rather than treating them as successful
  empty results.


## Consequences

### Positive

- Users can search for metadata candidates while editing a book, without
  spending provider calls merely by opening its detail page.
- Explicit acceptance keeps the user in control and prevents uncertain catalog
  matches from silently replacing data.
- Android queries the public catalog APIs directly, avoiding the backend's
  shared provider quota.
- Using the normal repository update path preserves offline-first behavior and
  synchronization semantics.

### Negative

- Catalog results may be incomplete, stale, or mismatched; users must inspect
  candidates before accepting them.
- Google Books API keys included in a mobile application can be extracted from
  the APK. Restrict the key to the Books API and apply suitable quota limits;
  use a backend proxy if the key must remain confidential.
- If one catalog is unavailable or rate-limited, only the other catalog's
  candidates are returned.

## Alternatives considered

### Automatically fill missing fields

Rejected because a plausible catalog match may refer to a different edition
or book. User approval is required before changing a record.

### Search candidates from backend

Rejected because routing client-initiated searches through the backend would
consume the shared provider quota. Android queries the public catalog APIs
directly.

### Search automatically when opening a book

Rejected because catalog calls are limited and users may not want to search
every book they view. A button makes each lookup explicit and lets users refine
the form's search terms first.
