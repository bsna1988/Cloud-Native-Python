# ADR 0009: Support for Hosted Public Image URLs in Book Catalog and Backend API

- **Status:** Accepted
- **Date:** 2026-10-31

## Context

When books are discovered or enriched via catalog services like Google Books API or Open Library, public cover image URLs (such as Google Books `imageLinks.thumbnail` or Open Library `covers.openlibrary.org` cover links) are frequently available.

Currently, the backend API (`POST /api/v1/books` and `PUT /api/v1/books/{id}`) only accepts binary multipart file uploads (`images`). To attach a cover image from Google Books or Open Library, an application would have to download the image bytes locally and upload them as binary files to the backend server.

This approach has significant drawbacks:
1. **Server Storage Burden:** Storing duplicate image files on the backend host consumes disk storage rapidly.
2. **Server Bandwidth & Memory Load:** Downloading and re-uploading public images puts unnecessary load on both mobile clients and backend servers.
3. **Redundancy:** Public cover images hosted on reliable CDNs (like Google Books and Open Library) are already publicly accessible over HTTPS.

## Decision

Extend the HomeBooks backend API and Android client to support direct hosted public image URLs alongside binary image uploads.

### Backend API Extensions

1. **Accept `image_urls` in Request Payload:**
   - Update `POST /api/v1/books` and `PUT /api/v1/books/{id}` endpoints to accept an optional `image_urls` JSON array in request form/body (or inside `book` payload) containing remote HTTP/HTTPS image links (e.g. `["https://books.google.com/...", "https://covers.openlibrary.org/..."]`).
   - Validate provided `image_urls` to ensure they are valid HTTP/HTTPS URLs.

2. **Combine File Uploads and Hosted Image URLs:**
   - The backend stores both uploaded local image filenames (e.g., `/uploads/<uuid>.jpg`) and hosted remote image URLs directly in the database (`book_images` table).
   - If both binary files and remote `image_urls` are provided, the backend retains all valid images for the book and sets the first available image as the book's `thumbnail`.
   - For `PUT /api/v1/books/{id}`, the backend supports removing specific image URLs (both local `/uploads/...` paths and remote `https://...` URLs) via `removed_images`.

### Android Client & Catalog Integration

1. **Extract Image Links from Catalog APIs:**
   - Update `CatalogMetadataClient` and `BookMetadataCandidate` to parse image thumbnail URLs returned by Google Books (`volumeInfo.imageLinks.thumbnail` / `smallThumbnail`) and Open Library (`https://covers.openlibrary.org/b/isbn/{isbn}-L.jpg` or `id`).

2. **Metadata Candidate Selection:**
   - When a user accepts a catalog candidate or creates/enriches a book from a catalog match, the candidate's remote cover image URL is included in the book record as an image link.

3. **Synchronization (`SyncWorker`):**
   - When syncing created (`CREATE`) or updated (`UPDATE`) books to the backend, `SyncWorker` includes remote image URLs in the request payload without re-downloading or re-uploading binary image files.
   - Local user-captured photos (e.g. camera/gallery) continue to be uploaded as binary multipart files (`images`).

## Consequences

### Positive

- **Reduces Backend Storage & Bandwidth:** Publicly hosted cover images are referenced directly without storing duplicates on the backend server.
- **Faster Sync & Reduced Mobile Data Usage:** Android clients do not need to download and re-upload large image files when using catalog covers.
- **Flexibility:** Supports a hybrid approach where user-taken camera photos are stored on the server, while official cover art is referenced via public CDN URLs.

### Negative

- **External Dependency on Image Hosts:** If an external image URL changes or becomes unavailable, the cover image link may break.
- **Mixed Image Schemas:** App and backend must handle both relative local upload paths (`/uploads/123.jpg`) and absolute HTTP/HTTPS URLs (`https://books.google.com/...`).
